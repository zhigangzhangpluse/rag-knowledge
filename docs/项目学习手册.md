# 知源 RAG 项目学习手册

**版本：2026-10-20。** 本手册依据当前源码编写。完整源码和逐行说明见 [HTML 参考手册](学习手册.html)，启动与评测命令见 [部署说明](deployment.md) 和 [评测说明](evaluation.md)。

## 本项目逻辑：从上传资料到回答问题

这个项目是一个带引用的文档知识库问答系统。用户先创建知识库并上传 PDF、Word 或 Markdown；FastAPI 接收文件并登记后台任务，解析器抽取文字、清洗、按标题和重叠窗口分块。BGE-M3 将需要新计算的分块变成向量，SQLite 保存知识库、正文、任务与有效版本，Milvus 建立向量索引。更新文档时先准备新版，确认向量写入成功后再切换有效版本；删除时先让文档退出检索，再后台清理数据。

提问时，系统先从 Redis 取同一知识库、同一会话的历史，把“试用期也可以吗”这类追问补成独立问题。然后 BGE-M3 只计算**问题向量**，Milvus 找语义近的片段，BM25 找关键词匹配的片段，RRF 合并两路名次，BGE Reranker 对少量候选重新排序。后端核对证据版本并编号；有证据时让 DeepSeek 依据原文回答，没证据时拒答，最后通过 SSE 逐段把回答和引用送到网页。**每次提问不重新向量化整库文档**；文档更新也只编码不能复用的分块。

```text
资料准备：PDF / DOCX / Markdown
       → 解析与清洗 → 带标题分块 → BGE 计算文档向量 → SQLite + Milvus

每次提问：用户问题 → 读取 Redis 历史并补全追问
       → BGE 计算问题向量 → Milvus 向量召回 + BM25 关键词召回
       → RRF 融合 → BGE Reranker 精排 → DeepSeek 依据证据回答
       → SSE 逐段送到网页，并展示引用
```

## 第一课：三个存储各管什么

**知识库**是业务概念，例如“员工制度库”和“产品说明库”；**SQLite** 是存储工具。它的 `KnowledgeBase` 表记录有哪些库，`Document` 表记录文件当前有效版本，`Chunk` 表记录分块正文和向量副本，`Job` 表记录后台处理状态。同一 SQLite 可以记录多个知识库，查询必须带 `kb_id`。**Milvus** 根据向量找近邻，并保存知识库、文档、版本等过滤字段；**Redis** 保存近期对话历史，键包含知识库 ID 和会话 ID，默认最多保留最近 12 条消息并设置过期时间。

例如员工手册 `active_version=2` 时，即使旧版分块尚未清理，检索仍只选 `version=2` 的分块；新版没处理好时，指针继续指向旧版。SQLite 的 `commit()` 只能提交 SQLite 事务，不能保证 Milvus 同时成功。因此更新时先准备新分块和索引，再切换有效版本，失败任务可重试。当前方案靠状态与顺序降低不一致影响，**没有跨库原子事务**。代码可对照 [`active_chunks()`](../app/retrieval.py) 和 [`ingest()`](../app/ingestion.py)。

```python
# 示意：有效版本由业务查询条件决定，不是 SQLite 自动猜出来的。
select(Chunk).join(Document).where(
    Chunk.kb_id == kb_id,
    Chunk.version == Document.active_version,
    Document.status != "deleted",
)
```

## 第二课：文件怎样变成可检索片段

[`parsing.py`](../app/parsing.py) 分三步：**解析格式**（PDF、DOCX、Markdown）→ **清洗噪声** → **切块**。Markdown 根据 `#` 标题、Word 根据标题样式保留层级；PDF 根据抽取结果和规则推断标题，并保留页码供引用。扫描版 PDF 往往只有图片，当前实现需要先经过 OCR 才能提取正文。长文档不宜整篇变成一个向量：“年假”和“机房设备”混在一块会稀释主题。当前按**字符**设置块大小和重叠，默认 `chunk_size=500`、`chunk_overlap=80`；程序还尝试靠近句末切开，所以实际边界不一定恰好是 500 字。字符数也不等于模型 token 数。

```text
原文：……申请条件 [连续文字] 年假天数……
第 1 块：前一段文字 + 交界处
第 2 块：交界处 + 后一段文字
                  ↑ 两块保留部分相同内容，避免条件和结论突然断开
```

`SHA-256` 在这里是内容指纹。文件哈希相同可跳过整份更新；分块哈希相同、模型名称相同可复用向量。分块哈希输入包含**标题和正文**，所以正文相同但标题不同也会被区分。它只识别清洗后完全相同的内容；“可休五天年假”和“年假为五天”不会因哈希相同而合并。

## 第三课：向量、BM25、RRF、Reranker 的分工

[`BGE-M3`](../app/models.py) 将单段文本编码成向量：文档向量在入库时算，问题向量在提问时算，Milvus 根据余弦相似度找候选。这里使用 BGE-M3 的**稠密向量**。`BM25` 则根据词语匹配召回片段，本项目先用 `jieba` 中文分词，适合补充错误码、产品型号等精确词。当前每次查询都会在有效分块上建立 BM25，便于小规模运行；大规模语料要考虑持久全文索引，分词和“只保留正分候选”的规则也会影响结果。

`RRF` 按两路**名次**融合，公式为 `Σ 1 / (60 + 该片段在某一路的名次)`，避免直接相加刻度不同的余弦与 BM25 原始分数。片段 A 在两路都排第 2 得 `2/62`，片段 B 只在一路排第 1 得 `1/61`，所以 A 更靠前。`BGE Reranker` 接着把“问题 + 候选原文”一起输入交叉编码器，只对召回的少量候选精排，**不能补回漏召回的段落**；Sigmoid 输出在 0～1 之间，不等于答案正确概率。最后按阈值过滤、按内容哈希去重。记住漏斗：**每路最多召回 `recall_k=30` → 融合后最多精排 `rerank_k=20` → 最终最多保留 `context_k=6` 条**，都是上限，不代表每题都有这么多证据。

本地 BGE 要下载权重、占内存；远程 Embedding 服务涉及网络、密钥和调用成本。换成 OpenAI、阿里云百炼、Cohere 等服务时，需为 `encode(texts)` 写适配器，处理各家的输入参数和返回格式，并用自己的中文业务题测试效果。换模型后，即使输出维度相同，也应重建文档向量和集合；不同模型的坐标空间不能直接混搜。当前生产配置使用本地 BGE，没有接入这些远程向量服务。

## 第四课：一次多轮问答怎么走

用户先问“年假几天？”，再问“试用期也可以吗？”。[`generation.py`](../app/generation.py) 从 Redis 取历史，把第二问补全为可独立检索的问题，例如“试用期员工能否申请年假？”。检索后，服务再次核对分块和文档有效版本，为证据编号 `[1]`、`[2]`，再让 DeepSeek 依据证据回答；**无有效证据时直接拒答**。改写只帮助检索，有引用也不能保证每句话正确：现有代码会检查不存在的编号和漏写引用，尚未自动验证每个结论是否被原文支持。

回答通过 SSE 发送。前端接收 `status`（进度）、`sources`（证据）、`delta`（回答片段）、`done`（完成与耗时）或 `error`（失败）。一个网络读取块可能只包含半个事件，所以 [`web/app.js`](../web/app.js) 用缓冲区拼成完整事件再解析。流式输出主要缩短用户**看到第一段文字**的等待感，不保证总耗时下降。

## 第五课：怎样验证和改进

先跑 [`scripts/check.ps1`](../scripts/check.ps1) 验证解析、版本、删除、会话与 SSE 等业务流程；自动测试使用替身，不衡量真实 BGE 的语义质量。真实服务联调方法见 [验收记录](verification.md)。评测数据在 [`eval/dataset.jsonl`](../eval/dataset.jsonl)，脚本比较纯向量、混合检索、混合检索加精排三种策略。`Recall@K` 看参考证据有多少进入前 K 条；回答正确率和引用支持率需按题人工标注，没标注应保持未知。现有 15 道虚构样本能检查流程，不能证明企业场景的泛化效果。调参时固定数据和模型，依次比较分块、召回、精排与时延，并另留未参与调参的测试题。

建议自己完成三次实验：① 将样例年假从 5 天改成 8 天，观察有效版本和引用；② 新建空知识库，确认不会读到其他库；③ 停止 Milvus 后上传，观察失败任务，恢复后重试。每次先预测行为，再运行，再对照源码解释原因。

## 面试常问八股文：直接按本项目回答

### RAG 与文档处理

1. **什么是 RAG？解决什么问题？** RAG 是“先检索外部资料，再让模型根据资料生成回答”。检索选证据，生成组织语言，引用让用户核对依据。它能减轻模型凭训练记忆编造的风险，但检索错误和生成错误仍可能发生。
2. **RAG 与直接把全文放进提示词有什么区别？** RAG 只选少量相关片段，减少上下文占用，也便于更新资料和追溯来源。代价是需要维护解析、索引和检索质量。

3. **为什么要分块并设置重叠？** 块太大容易混主题，块太小可能拆散条件和结论；重叠保存交界处上下文。本项目按字符窗口，并尽量在句末切分，具体大小需靠业务测试集选。
4. **标题层级为什么要保留？** “每年五天”独立看不出是在讲年假还是病假；加上“员工制度 / 休假 / 年假”有助于检索和引用定位。

5. **哈希去重和语义去重有什么差别？** 哈希能快速判断输入内容是否完全一致；语义去重要计算相似性，能发现不同说法表达近似意思，但阈值过低可能错删不同规则。
6. **每次聊天会重新向量化知识库吗？** 不会。入库时算文档向量；每次提问计算问题向量。文档变更时，仅新分块或改变的分块需要新向量，未变分块可在同模型条件下复用。

7. **换一个 Embedding 模型需要做什么？** 接入新模型接口，检查维度、归一化和查询/文档输入要求，重建文档向量及对应集合，并用相同评测集比较结果。维度相同也不能混用不同模型的旧向量。

### 检索与排序

8. **向量检索和 BM25 有什么区别？** 向量检索按语义空间找近邻，BM25 根据词项匹配和统计权重评分。前者有利于不同表述，后者有利于精确术语；项目将两路候选融合。
9. **什么是 RRF，为什么不直接把分数相加？** RRF 按各路名次计分再求和。BM25 分数和余弦相似度的刻度不同，直接相加容易让某一路凭数值范围占优势。

10. **Reranker 和 Embedding 有什么区别？** Embedding 单独编码问题和文档，适合提前建索引及快速召回。Reranker 将问题与候选原文配对计算，适合少量候选精排，计算开销更高。
11. **为什么先召回再精排？** 全库逐条交叉编码太慢。先用向量和 BM25 缩小范围，再对融合候选精排，在相关性和时延之间取平衡。

12. **Reranker 能修复漏召回吗？** 不能，它只能给已有候选重新排序。参考答案根本没进入候选时，要检查解析、分块、索引、分词、过滤和召回数量。
13. **Reranker 分数 0.8 能说正确率 80% 吗？** 不能。Sigmoid 输出是模型排序用的分数，未经过业务校准，不等同答案正确概率。阈值要根据有答案和无答案题共同评测。

14. **Recall@K 是什么？** 对一道题，把前 K 条里找到的参考证据数除以该题参考证据总数；多题再按明确口径汇总。它衡量“有没有找来”，不能单独证明回答正确。

### 数据、一致性与更新

15. **知识库和 SQLite 是同一个东西吗？** 不是。知识库是用户划分资料的业务容器；SQLite 保存这个容器、文档、版本和任务的结构化记录。查询用 `kb_id` 限定范围。
16. **SQLite、Milvus、Redis 各做什么？** SQLite 判定哪些文档版本有效并保存正文和任务，Milvus 根据向量找近邻，Redis 保存近期会话历史。它们分别承担业务状态、向量索引、短期上下文。

17. **为什么需要 `active_version`？** 新版处理期间继续使用旧版；新版向量写好后再切换指针。查询只认指针指向的版本，降低用户读到半成品的机会。
18. **SQLite 和 Milvus 能用一个 `commit()` 一起提交吗？** 当前实现不能。程序按顺序写入，失败任务允许重试；即使旧向量暂时残留，查询仍按 SQLite 有效版本过滤。这不是严格的跨库原子事务。

19. **增量更新如何节省模型计算？** 先比较整文件哈希；完全相同就跳过。文件变了再比较同一文档、同一模型下的分块哈希，复用未变分块的向量，只编码缺失的分块。
20. **删除文档后会立刻从磁盘消失吗？** 接口先逻辑标记，使文档退出检索，再由后台任务清理 Milvus 向量、上传原文和 SQLite 分块。后台清理失败需要排查并重试。

21. **幂等和“只执行一次”一样吗？** 不一样。幂等指重复执行后仍得到预期最终状态；本项目用稳定分块 ID 和向量 upsert 减少重试重复写入，并没有保证任务只运行一次。

### 多轮、流式与可靠性

22. **Redis 为什么按知识库和会话双重隔离？** 相同 `session_id` 在不同知识库中不应共用历史，否则追问可能带入其他库的信息。当前 `kb_id` 负责业务范围；公开多用户部署仍需单独增加用户鉴权。
23. **为什么多轮追问需要改写？** “试用期呢？”缺少检索关键词。结合历史补成独立问题可以提高召回，但改写可能误加事实，所以回答仍要回到当前证据。

24. **SSE 与 WebSocket 如何选？** SSE 适合一次请求后服务端持续送进度和回答；WebSocket 适合长期双向消息。此项目用 HTTP 请求提交问题，再从同一响应读取 SSE 事件。
25. **只要 HTTP 返回 200 就表示回答成功吗？** 不能这样判断。流式响应头已经发出后，模型或 Redis 仍可能失败；前端应根据 `done` 或 `error` 事件判断是否完成。

26. **有引用编号就代表答案可靠吗？** 编号存在只能说明格式和来源对象存在。还要检查原文是否支持相应结论、是否漏掉条件或使用了过期版本；目前人工评测负责语义支持检查。
27. **证据不足时怎样拒答？** 当前检索后若没有有效证据，服务直接输出拒答文本；有证据时也用提示词要求模型说明不足或冲突。提示词和编号检查无法完全杜绝幻觉。

28. **如何证明优化真的有效？** 用固定且带标注的业务题比较 Recall@K、答案正确率、引用支持率与首段/总耗时。现有 15 题只是流程样本；增加真实场景和独立测试题后才能讨论效果提升。

## 面试介绍这项目时怎么说

> 我做了一个 FastAPI 文档知识库问答系统。上传 PDF、Word、Markdown 后，后台按标题分块，使用 BGE-M3 向量化并写入 Milvus；SQLite 保存正文、任务和有效版本，更新时复用未变化分块的向量。提问时先利用 Redis 历史改写追问，再把向量检索与中文 BM25 的候选用 RRF 融合，经过 BGE Reranker 精排后交给 DeepSeek 依据证据回答。前端用 SSE 展示回答与来源，空证据时拒答。我用自动测试和小样本评测检查了版本隔离、删除、引用和检索流程；当前系统是本机单用户实现，真实业务效果仍需要更大规模的标注集验证。

这段介绍只陈述项目实际实现。讲到指标时，说明测试集规模和标注范围，不把演示模式结果或未标注的正确率说成生产性能。
